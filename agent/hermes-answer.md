# Hermes 回复信息过载复盘报告

## 一、总述

本次问题的核心不是 Hermes 信息不足，而是回复没有按用户当前决策需求做过滤和分层。它把「工作状态汇报、内容变化观察、规则变更提案、授权请求」揉成一段，导致汇报与回答错位、决策点后置、事实与推断混杂。根因可归纳为：任务对象漂移、多目标消息未分栏、授权边界不清、缺少用户建模。

## 二、分述

### 1. 主要表现

- **汇报与回答错位**：前 80% 是提交哈希、指针状态、三方一致、文件改名等审计信息，真正的决策点「要不要现在改 skill 和 README」被压在最后。
- **信息层级缺失**：已完成事实、观察推断、规则提案、待确认事项混在一起，读者难以判断哪句是结论、哪句是猜测、哪句需要批准。
- **电报体牺牲理解效率**：大量箭头、括号、缩写和高密度事实，压缩的是字符数，不是读者的理解成本。
- **判断被假设句稀释**：Hermes 已形成「新文体是按交付物分节」的判断，却用「若确是这个意思……」把确认负担推回给用户。
- **内部推理外溢**：「比我上一条猜的……」属于思维过程，不是交付物。

### 2. 原因分析

1. **任务对象漂移**：它回复的不是「用户当前的问题」，而是「这一轮做过的所有事」，把回答变成了工作交接。
2. **多目标消息未分栏**：已完成、已推断、待确认、建议默认动作四类信息没有分开，造成时态和权责混乱。
3. **提示冲突**：可追溯、极致压缩、主动推进、不越权同时作用，形成「证据很多、决策很晚」的确认焦虑。
4. **授权边界不清**：有判断但不敢直接给方案，只能用假设句请求确认。
5. **多轮上下文粘连**：主动延续上一轮讨论，但用户已不需要推理链。
6. **缺少用户建模**：未区分「判断是否改 skill 的高价值信息」和「哈希、指针等低价值状态噪音」。

### 3. 影响

- 用户理解成本高，需要自行解码和筛选。
- 关键决策点被淹没，回复显得混乱、过度辅助。
- 容易让用户误以为 agent 在推卸判断责任或过度汇报。

### 4. 改进措施

- **输出契约**：结论先行；只列与当前问题相关的信息；变更只给文件和关键 diff；哈希、指针、仓库状态放附录。
- **四栏结构**：已完成 / 已推断 / 待确认 / 建议默认动作。
- **事实与推断标注**：明确哪些是观察到的事实，哪些是推测。
- **减少内部推理外溢**：不展示「我上一条猜了什么」这类过程性内容。
- **明确授权边界**：规则变更给出默认方案，只有越权或高风险时才请求确认。
- **默认执行策略**：能按既有口径推进的直接推进，不要用大量上下文铺垫后再问「要不要」。

## 三、总结

一句话：Hermes 的问题不是话多，而是没有把「汇报、分析、提案、请示」分层，也没有按用户当前决策过滤信息。改进关键不是单纯「少说」，而是建立输出契约：先给结论和待决项，再按需展开；状态细节放附录；规则变更给默认方案，仅越权时确认。
